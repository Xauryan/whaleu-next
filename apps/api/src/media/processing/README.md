# S1 image processing boundary

Static implementation only. No sharp installation, typecheck, tests, build or actual image decoding has been executed in this pass. No production wiring is added.

- `IsolatedSharpProcessor` requires an explicitly configured trusted deployment launcher. Ordinary process execution is unavailable. The child independently reads existing cgroup-v2 memory/swap/OOM controls and a capped private tmpfs; it never mounts filesystems or changes controls. A pre-existing dedicated container may provide these facilities. A Node heap flag is not a native RSS bound. The external launcher also owns the hard watchdog, kill/cleanup and host filesystem/network isolation; its contract still needs platform acceptance.
- `RegisteredSyntheticSharpProcessor` is a distinct test-only path for an exact immutable SHA-256 whitelist (at most 64 synthetic inputs). It checks actual bytes before spawning, and the child rechecks before decoder import/use. It uses real sharp, bounded streams and deadline termination, but does not claim hostile-input RSS or temp-disk acceptance. Do not register it in AppModule or populate its whitelist from requests. It is not a reviewer or a readiness issuer.
- The optional dynamic `sharp` import fails unavailable until the approved dependency is installed and pinned. It is deliberately not replaced by a fake decoder. The launcher must expose the built worker and dependencies; source-mode fixtures use the repository's existing tsx loader.
- The child fully decodes to raw pixels, normalizes orientation, then reencodes fixed JPEG/PNG variants without preserved metadata. APNG and MPO/concatenated JPEG are rejected. Both sides enforce input/output byte budgets; parent independently hashes the exact protocol bytes. Variants remain buffers until the caller writes exact immutable destinations and passes their independently measured evidence to `sealProcessedManifest`.
- A manifest is immutable processing evidence only. It grants no Review approval, readiness, attach permission or delivery permission. Persistent object attempts and recovery belong to orchestration.

Read-only current capability inspection on 2026-10-10: Linux; `/proc/self/cgroup` reported `0::/`; cgroup limit files were not exposed at `/sys/fs/cgroup`; no `/media-work` capped tmpfs mount was present. This does not prove the outer host lacks limits; it means this worker cannot verify the requested dedicated isolation here. No security setting was changed.

Official contracts consulted: https://sharp.pixelplumbing.com/api-constructor/ , https://sharp.pixelplumbing.com/api-output/ , https://sharp.pixelplumbing.com/api-resize/ , https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html . Version pinning and actual sharp/platform behavior remain acceptance gates.
