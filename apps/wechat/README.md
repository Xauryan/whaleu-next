# Native WeChat community, errands, safety and own-account slices

This is a greenfield TypeScript/WXML/WXSS Mini Program. It is **not a complete WhaleU app** and must not replace production. Login and session management now have native pages and a concrete new-API gateway. Campus search/selection and own nickname, bio and eleven explicit preferences have native forms. Community C1 now has native regional/global feed, detail/root comments, text composer, desired-state likes, own deletion and durable publication recovery. The C2A poll slice adds structured composition, immutable one-time voting and durable ballot recovery. C2B adds flat reply threads, target navigation, comment/reply reactions and author root pins with durable interaction recovery. C2C adds regional trading listings, chosen contacts, exact prices and durable owner resolution changes. C2D adds post-based group formation, immutable joining and member-only chosen-contact access. Local reporting, immutable post juries and independent owner-only system notices now have native flows. It remains a partial slice: production authority issuance and onboarding, phone/student verification applications and binding, remaining moderation/admin features, binary media upload and all retained later business features are unfinished. Unknown runtime facts fail closed. General publication remains unavailable while there is no trusted review issuance workflow.

## Runtime policy and publication availability

- The strict public capability DTOs remain unchanged. Authorization-eligible `authorModes` and `canDisableComments` are advisory hints, not publication approval. Normal runtime overall post/comment availability stays `unavailable` with `CONTENT_REVIEW_UNAVAILABLE` when no review issuance workflow can fulfill a fresh publication. A known eligibility denial retains its denial reason; missing facts remain unavailable
- The composer saves editable drafts but cannot create a new request unless overall availability is `allowed`. Changing identity mode, category, browsing campus or comment policy does not bypass that check. Existing unit fixtures with `allowed` exercise the client contract only; they do not demonstrate a live approval workflow
- Feed continuation and existing readable content, likes, saves, update preferences, poll votes and formation joining use their own server decisions. They do not fetch publication capabilities or require a student number. A publication capability/verification-summary failure cannot turn a readable post into absent content or disable otherwise authorized phone-only interactions
- Root/reply identity choices follow their separate backend capability. The client does not infer related versus foreign publication, verified cross-region anonymous-comment permission, affiliation, management scope or identity-campus validity from a browsing choice or profile. Own anonymous-post forced mode remains preserved. No client permission, approval, provenance, scope override or synchronization field has been added
- Missing approval/authority errors remain transient, not terminal rejection receipts. Original account/origin-bound publication recovery runs before profile/capability/parent reads and can recover a minimal receipt after review, identity selection, current eligibility or parent visibility changes. Unknown results preserve the exact original intent. Account/login changes and page/app hide cancel stale callbacks and clear visible private state
- Browsing-campus selection is the existing preference only. The separate identity-campus selector uses current own-account status and eligible options; trusted moderation decision issuance, topology/configuration administration, phone binding and affiliation onboarding remain unfinished. The local runtime acceptance harness uses canonical synthetic input facts; this is not completed user onboarding. Native offers no fake completion or grant control
- Media remains explicitly unavailable, with no chooser/upload enablement. Related synchronization, regional/global aggregate-feed parity, real providers, historical import, real grants and production deployment remain outside this increment

`test/community-runtime-policy.test.ts` checks the unchanged closed contracts, rejected authority injection, unavailable versus terminal receipts, independent interactions, separate root/reply mode handling and lifecycle ownership. `scripts/smoke-runtime-policy.mjs`, run by `npm run build -w @whaleu/wechat`, executes emitted native page handlers with the real gateway/decoders against synthetic responses. That compiled smoke is distinct from the separate real-AppModule HTTP/PostgreSQL acceptance suite. Neither establishes WeChat DevTools rendering, physical-device or provider acceptance.

## Community C1 and recovery

- `WhaleuApp.community` is the typed root facade. Native pages and small controllers reuse the existing session/API transport, cancellation and login-epoch ownership. There is no legacy wire adapter, fake post feed or synthetic verification switch in runtime code
- Feed navigation resolves the selected physical campus through the explicit community-space endpoint before requesting posts. Missing or inactive mapping stays unavailable. Switching to a global space is explicit; an institution code is never a region/space/identity grant
- Public visitors choose a campus from the real catalog and see the first-ten preview; signed-in phone-unverified users receive a distinct continuation blocker. Invalid supplied credentials cannot turn into a guest request. Every page/load-more result is scoped to account, login epoch, space/category and request generation
- Detail clears previous body/media/comments before refreshing and only exposes comments after a current parent visibility decision. A missing, hidden or deleted parent clears dependent content. Anonymous tagged decoders reject extra real identity fields, and anonymous comments cannot use a named parent's `isPostAuthor` flag to disclose the hidden relationship
- Post and root-comment composers show the effective identity. Defaults express intent only: a disallowed anonymous selection never becomes named silently. Own anonymous-post comments are forced anonymous; independent comment capabilities avoid incorrectly applying post-publishing policy. Identity-default conflicts require an explicit choice
- Editable drafts and frozen pending attempts use distinct API-origin/account-scoped storage keys. A UUIDv4 and exact CRLF-normalized text, operation, target, author mode, ordered completed asset IDs and comment policy are persisted and read back **before** dispatch. One account can have only one unresolved publication across posts/comments. UUID generation uses the native random-byte API with a deadline and fails closed if unavailable
- Timeout, cancellation, close/hide, 5xx, malformed response, auth failure and account switch preserve the frozen original intent. The page disables edits/replacement and offers receipt lookup or identical-request retry. `REQUEST_NOT_FOUND` never unlocks the form. Only a validated account-owned terminal receipt settles it; a stored created receipt remains recovery after content deletion
- Account changes clear private page/form state synchronously but retain the original account's pending recovery record. Same-account re-login can explicitly recover it. Successful publication clears its editable draft before releasing the pending protection. Local storage failures prevent first dispatch or retain the recovery barrier
- Likes use desired-state PUT/DELETE with one operation per target; duplicate taps do not toggle twice. Own deletion has a separate confirmation step and only changes body/count state after a known 204, or clears pending display and requires reconciliation after uncertainty
- Image publishing is **PARTIAL**. DTOs and recovery retain bounded asset IDs, and existing approved media views have strict HTTPS decoders. There is no binary chooser/upload/progress/preview/approval workflow yet, no image URL entry and no pretend successful upload. The UI says the feature is unavailable
- Own-publication recovery lists contain only IDs, scope, category, status and time. They never return hidden/deleted bodies or media

Community contracts live in `../../docs/API_COMMUNITY.md`. Later discovery/distribution, remaining trading parity, directory write/admin/media workflows and chat, internal links, subscriptions, notifications/rewards, moderation/admin workflows and all other master-plan features remain retained scope. Synthetic fixtures are confined to tests and do not establish real provider or device acceptance.

## C2A polls and immutable ballot recovery

- Post composer supports a separate poll question, single/multiple choice, and 2–5 total ordered options. At least two ordinary options are required; the optional final `吃瓜🍉` defaults on and consumes one slot. Question/option new writes use 255 Unicode codepoints, reject blanks/trimmed duplicates, preserve whitespace and normalize only CRLF. Post body remains required. Poll and formation components are mutually exclusive; internal-link variants and conflicting extra fields reject. Trading composition offers none of these components
- Poll fields persist with the editable account/origin/target-scoped draft. Publication freezes the entire structured component before dispatch. Unknown outcomes never rewrite question/options or request identity. Existing C1 no-component frozen payloads remain unchanged, including on retry
- Detail performs one parent-visible poll fetch per load or settled-ballot refresh, with no per-feed N+1 fetches. Imported raw question/labels are preserved without the new-write length/control rules; existing dated polls display their deadline/expiry. New composition offers no deadline picker and sends no deadline
- Single choice submits on tap; multiple choice keeps selection local until explicit confirmation. Author voting is supported. Server-owned `canVote` and its exact reason govern the UI independently from post publication/student-identity policy. Unavailable/phone/restriction states remain explicit and fail closed
- Every vote freezes UUIDv4, target and canonical selected-option set into a separate durable ballot namespace scoped by API origin and active account. Persist-and-read-back precedes dispatch. One unresolved ballot per account blocks replacement intents, including on another poll; publication recovery remains separate
- Timeout, cancellation, malformed/error results, Back/page close, app hide, account replacement and restart retain the original attempt. Matching owner-only terminal receipts alone settle it. `REQUEST_NOT_FOUND`, `BALLOT_NOT_FOUND` and even an own-ballot status read never prove the original request cannot still commit or unlock a new key. The own-publication page exposes the original poll recovery link
- Recovery works after the parent is hidden/deleted through minimal account-owned receipt/status routes, without loading hidden question/options, aggregates or identity. No voter IDs, voter lists, other people's choices or anonymous identity resolution enter poll DTOs. The developer identity overlay remains separate and transient
- Committed choices are read-only; there is no revote/unvote, optimistic durable count, or creator edit/close control. Current aggregates refresh after confirmation. Native result bars appear after voting or expiry, although eligible readers already receive aggregates from the API: this UI reveal flow is not a secrecy boundary. Voter count and selection count are labeled separately; percentages use total selections
- Strict real gateway/status/receipt decoders cover target identity, counts, immutable own choices and nested privacy. Synthetic tests exercise structured drafts/publication, optional-final slot, repeated taps, auth refresh, status mismatch, storage failures, unknown commit, cancel/reopen, same-account login/account switch, app-hide, historical expiry/raw text and regional/global parent scope. Compiled native smoke executes poll handlers and durable app-hide recovery without a provider/network

Runtime authority consumes only validated owned facts; unknown facts remain unavailable. Review issuance and media workflows remain unfinished. This slice does not establish full C2, provider acceptance, actual WeChat DevTools rendering or physical-device acceptance. Remaining trading parity, group directories/chat, internal links, subscriptions, notifications/rewards, complete drafts/preferences and the full parity backlog remain required.

### Developer-only identity overlay

The foreground feed/detail/thread pages automatically request fresh server authorization for visible content. Only a server-confirmed developer can request the separately audited identity endpoint; school/super administrators do not gain this privilege through hierarchy inference. The overlay is a separate in-memory view, never merged into ordinary post/comment/reply DTOs, drafts, storage, logs or sharing state. It displays authoritative UID/nickname and a verified student number only when supplied; unavailable student verification and real avatars remain explicitly unavailable.

Every target change and request begins by clearing the old overlay. Permission denial, incomplete/failed batches, logout, login-epoch/account replacement, page hide/unload and the root app-hide boundary cancel and clear it. Late callbacks cannot repopulate a new view. A display TTL of at most 30 seconds, bounded by the access-token lease captured for each request, clears sensitive values until the user refreshes content and authorization is checked again. Responses arriving after that lease cannot render, and an unrelated refresh cannot extend an older response’s lease. This is bounded client retention, not a claim of instant remote revocation notification. Role grants are never seeded or user-selectable.

## Own identity-campus selection and recovery

- `WhaleuApp.identityCampus` and the dedicated Chinese page use authenticated own-account status/options, selection and minimal receipt endpoints. Profile, verification and compose link to this page; the browse-campus page remains a separate preference. Candidate visibility is independent of phone/safety write eligibility. Missing history, known required, stale bindings, known-empty options and unavailable input coverage are distinct; unknown affiliation never forces a new application or student-number backfill
- A current valid campus may be highlighted, but neither page load, a singleton list nor restored state saves anything. Choosing a campus opens an explicit physical-campus/operating-region confirmation. Same-campus renewal is supported after input revisions change. Selection grants no school certification, student-number verification, role, admin scope or content approval
- Each confirmed choice durably stores and reads back only `{ version, accountId, requestId, campusId, expectedStateRevision }` under an API-origin/account-specific key before PUT. No credentials, affiliation evidence, status/option caches or browse preference are copied. Duplicate taps cannot replace the immutable request. Timeout, network loss, auth failures, malformed responses, missing receipts, hide/unload and login changes preserve recovery for the original account
- Cancel before dispatch cannot write. After dispatch, Cancel means stop waiting, not rollback. Receipt lookup or identical retry remains possible after same-account reauthentication. Only a matching success receipt, or a definitive exact-PUT revision conflict under the server's receipt-first serialization contract, releases the journal. A version conflict refreshes state and requires a new explicit confirmation; generic conflicts and missing receipts never unlock it
- Success settles the historical receipt and separately queries current status. Superseded, unavailable and failed refresh results cannot make the old receipt current authority. Page/app hide and account/login-epoch changes synchronously clear private display and reject late callbacks; returning performs a fresh read or restores the pending barrier
- Compose navigation is offered only with a reliably saved editable draft. Posts, root comments and replies keep exact drafts and original targets; returning requires another explicit send. Generic community unavailability is not relabelled as a required identity choice. Publication independently rechecks current scope and approval; selector success cannot send, retarget or reopen an old terminal publication key
- Strict decoders, gateway tests, lifecycle/recovery tests, draft regressions and an emitted-page smoke cover this bounded flow. Real AppModule synthetic HTTP/PostgreSQL acceptance is separate. WeChat DevTools/device rendering, production input reconciliation, provider workflows and actual user eligibility remain unverified

## Own-account verification summary (read-only)

- `WhaleuApp.verification` has a real authenticated `GET /v1/me/verification` gateway and a dedicated native Chinese page, linked from profile/status. Returning to the page always starts a fresh read. Startup never calls a provider or requests verification
- The exact response contains only four nested status records: `affiliation`, `studentNumber`, `phone` and `application`. Facts independently support `verified`, `unverified`, `unavailable`, `expired` and `revoked`; applications support `none`, `pending`, `rejected` and `unavailable`. Unknown fields/statuses, private values and non-200 success responses are rejected
- Unknown/unavailable is visibly distinct from unverified. Verified affiliation with no verified student number is valid and expected; missing or overloaded historical number fields are preserved for later reconciliation, never interpreted as failed affiliation or a reason to force re-verification. Improving student-number coverage and any future institutional sign-in integration are deferred, with no backfill or provider activation in this slice. Phone ownership stays independent. Pending or rejected applications never imply verification. Browsing campus, public UID and administrative role do not supply verification facts or permissions
- The page receives no student number, phone value, legal name, institution guess, evidence, provenance or arbitrary account selector. Neither raw summaries nor rendered status are persisted, logged, placed in share state or added to ordinary community DTOs. The developer-only overlay remains on its existing separately authorized/audited endpoint
- Every query clears the previous snapshot before dispatch. Login-epoch/account replacement, logout, page hide/unload, root app-hide and cancellation synchronously clear the display, abort work and reject late results. Background reload is suppressed until the page is reopened. Repeated taps cannot duplicate an active query; one expired-access refresh is allowed for this read only, and a delayed old-token failure cannot erase a newer credential
- All permission/error/absence paths keep verification unconfirmed. Status snapshots are not operation permissions: actual capabilities are checked by the server at use time
- This is **only a read-only status slice**. Student application, evidence upload, reviewer UI, reapplication and native phone authorization/binding are visibly pending, with no pretend submission or success buttons. No real provider is enabled by this page

The ledger API contract is documented in `../../docs/API_VERIFICATION.md`. Synthetic decoder, gateway, controller and compiled-page smoke tests cover independent states, affiliation-only approval, revoked/expired records, cancellation, auth refresh, account switching, app/page hide, late callbacks and no persistence. Actual WeChat DevTools/device layout and real provider acceptance remain unverified.

## Identity foundation

- Native WeChat login, session verification and logout UI, composed from a small `wx` adapter and typed application controller
- A concrete `HttpAuthGateway` with explicit HTTPS origin, endpoint-specific status/DTO validation, cancellation, independent deadlines and sanitized errors
- Direct new-API identity contracts:
  - `POST /v1/auth/wechat/login` with `{ code }` → credentials, HTTP 200
  - `POST /v1/auth/refresh` with `{ refreshToken }` → rotated credentials, HTTP 200
  - `GET /v1/auth/session` with bearer access → session metadata, HTTP 200
  - `POST /v1/auth/logout` with bearer access → no body, HTTP 204
- Credential DTO: `{ accountId, sessionId, accessToken, refreshToken, expiresAt, refreshExpiresAt }`; session metadata contains those fields except tokens. IDs are UUIDv4, timestamps are integer epoch milliseconds, access expires no later than refresh. Tokens are purpose-separated `wu_a_` / `wu_r_` plus 43 base64url characters
- A validated, single-record session store scoped to the reviewed API origin. Restore uses the same concrete identity decoder; credentials from another environment or an old unscoped key are never imported
- Single-flight refresh, one explicitly allowed replay for read-only session checks, and account/login-epoch/session guards
- Visible unconfigured/provider-unavailable, rejected/expired/revoked login, blocked account, timeout, cancellation, storage and uncertain-logout states
- Synthetic adapter and controller tests for interrupted login, repeated taps, page disposal, restored-session checks, concurrent refresh, account changes, malformed responses and native timeout/cancellation callbacks

No tokens, provider codes, provider IDs or invented profile data enter page `setData`. Native platform and server diagnostic text are not displayed or logged. Only whitelisted error codes and a validated correlation ID are retained.

Only `ACCESS_TOKEN_EXPIRED` with HTTP 401 can trigger refresh. Ordinary network errors never retry a mutation. Refresh tokens are one-use: **any failed or uncertain refresh clears the current local login and requires fresh login**. A lost response is never treated as permission to reuse that refresh token. Shared refresh continues for other callers if one cancels its wait.

Logout clears memory synchronously before server revocation, and same-tick logout prevents pending login/refresh dispatch. Server revocation uses the captured old access credential and cannot clear a newer local login. If server revocation is unconfirmed, the UI says so. Storage removal can fail; the UI warns that persisted credentials may remain and may require clearing the Mini Program cache. This is not a claim of encrypted storage or guaranteed erasure.

## C2C trading listings, voluntary contacts and durable resolution

- The regional feed defaults to ordinary browsing without a category filter. Normal trading listings can appear there; urgent listings are excluded by the server and rejected by the gateway if leaked into this ordinary result. Explicit `trading` browsing includes both modes and all thirteen original keys: `qiugou`, `shuma`, `shujia`, `yifu`, `meizhuang`, `yundong`, `riyong`, `shipin`, `kaquan`, `xiangbao`, `zixingche`, `diandongche`, `xianshiqi`. Subtype filters reset cursors and cancel superseded requests. Global feeds never offer trading
- The integrated Chinese composer requires named identity, nonblank post text, exact positive decimal price at most 99,999 yuan, manually chosen location and at least one voluntary WeChat/QQ/phone contact. Sale defaults to urgent; wanted forces normal. No poll/group/link controls are available for a trade. There is no fake media upload; approved historical images still render through the existing media contract
- Price is a plain ASCII decimal string with at most 100 input characters. No binary floating conversion, fixed two-decimal assumption, rounding, currency suffix, exponent, junk, zero or coercion is accepted. Canonicalization removes only redundant numeric zeros. Location new writes use 200 UTF-8 bytes and each contact 50 bytes, matching the chosen server contract. Original native location UI had a narrower ten-character input; the new composer deliberately uses the source-server limit and rejects overruns instead of truncating
- New writes and historical reads are separate. Display prices are tagged exact amounts plus nullable raw provenance, or raw legacy text only. Categories are tagged known keys plus nullable raw provenance, or unknown raw legacy text. Historical location and contacts retain original text and controls, with only valid-Unicode and 1 MiB display-string safety checks. Unknown categories are displayable but cannot be silently mapped into a new listing or filter. These synthetic projection tests do not establish a real import or migration acceptance
- The user must affirm contact visibility before publication. No verified phone, identity-campus field or private profile contact is inferred or copied. Chosen contacts and manual location survive incomplete local drafts. After a matching created publication receipt, the complete chosen contact set and location are remembered in a separate account/origin-scoped local preference record; clearing one field replaces its previous remembered value. New composition requires contact consent again. These are **client-only partial preferences**: original server-backed publishing preferences, cross-device behavior and migration remain required. Storage failure keeps publication recovery protected
- Public feed/detail post DTOs and own listing results contain no contacts. An explicit detail action requests the authenticated parent-gated contact endpoint; every clipboard action fetches it again. Copy preserves the literal value, never guesses a phone number, calls it, crawls a URL or opens another app. Contact responses stay in transient view state and clear before a new request, parent reload/access loss, cancel, account/login replacement and page/app hide. The developer identity overlay remains separately authorized and never supplies contact data
- Resolved listings disable contact reveal/copy for everyone, including the owner, while retaining chosen values in backend storage. Starting resolution or recovering an unknown result synchronously clears contacts and cancels old reveal/copy work. Unrelated detail renders and late post callbacks cannot re-enable access: the page requires a post read begun after the latest mutation/recovery barrier, with no pending mutation, and an open projection. Denied contact checks also require a new parent read. A reopen or old receipt never restores cached values; a new authorized GET is required. Clipboard work already handed to the platform cannot be recalled
- Owner `open`/`resolved` changes use a dedicated status controller and origin/account-scoped nonexpiring journal. The exact target, resolution and UUIDv4 are stored and read back before dispatch. Repeated/opposite actions, another listing and another page cannot replace an unknown intent. This namespace cannot overwrite C1 publication, C2A ballot or C2B discussion journals

## Errands E2B: scoped commands and global restriction management

- The administrative journal is separate from the E1 lifecycle journal and is isolated by API origin/account. Loss of authority, a different fixed school, malformed replies or authorization-unavailable errors clear the underlying management rows/counts/controls; unresolved recovery is retained. - Closing a modal, changing search/filter/target, hiding a page, root app hide, Safety invalidation or account/login-epoch changes cancel stale callbacks and clear transient bodies/form reasons. Cancellation does not claim to undo an already dispatched command. A late applied response after dismissal cannot settle the journal or repopulate hidden data. ## Optional semantic community search client

The search page defaults to keyword mode and offers an explicit semantic mode.
Semantic search calls the separate `/v1/community/search/semantic` endpoint with
the same scope/type/date/topic filters but no cursor. It accepts only the closed
`mode=semantic`, `indexStatus=current`, `ranking=embedding-top32-reranked` envelope
and lightweight hits. Original snippet segments may all be unhighlighted; the
client never invents literal matches, raw scores, totals or exhaustive coverage.
Semantic results have no pagination and are labelled as limited related results.

The backend is disabled by default. `SEMANTIC_SEARCH_DISABLED` visibly says the
service is not enabled; `COMMUNITY_UNAVAILABLE` stays unavailable, never empty.
Both keep the draft and submitted query, and neither silently falls back to
keyword search. Switching modes explicitly cancels previous work and reuses the
submitted query; draft edits remain unsubmitted. Scope, account/login epoch,
safety, cancel, page/app hide and reopen retain the existing stale-response fences.
Navigation carries only current structured IDs and destination owners reread the
current parent/root/reply. No provider credentials or activation controls are
shipped in the client. Unit tests and emitted-handler/bounded-WXML smoke use
synthetic responses; they do not establish real provider or physical-device QA.
