# Large Community discussion reads

This later business correction replaces the 1,024-child serialization ceiling. It is not a change to the frozen Home layout, specialist Window/Major discussion contracts, publication permissions, or production activation.

## Count contract

- A Community Post has either three exact safe-integer fields (`commentCount`, `replyCount`, `discussionCount`) with an exact safe sum, or three `null` fields.
- A Community Comment has an exact safe-integer `replyCount` or `null`. Its readable preview is independent of count availability.
- Null has one generic meaning: the exact current count is unavailable. No timeout, hidden-author, block, source, or failure reason is exposed. No partial prefix, estimate, false zero, or raw database total is substituted.
- Root and reply counts use the same canonical Review, parent structure, category, Media, named relationship and owner-hidden visibility semantics as discussion content. Detail children preserve outgoing-only list relationship rules. Author-private hidden detail does not become public discovery.
- Official-account export still requires exact counts. Initial uncertainty or late proof invalidation aborts the export transaction, including after a numeric value has been copied into an internal manifest.

## Resource and authority bounds

Candidate enumeration and canonical snapshots stream in batches of at most 256, with a single sentinel and existing snapshot byte/node limits. All posts and selected roots in one transaction share a 2,000 ms monotonic optional-source budget, not a fresh budget per item. Existing statement/lock limits and savepoint recovery remain in effect.

One fixed-size final owner epoch proof covers the transaction's discussion counts. An epoch change conservatively invalidates all bound optional count fields, not separately authorized content. Unsupported writer-capacity deployments retain the existing at-most-1,024-candidate exact fallback and share a single 500 ms final fallback budget across every field. Failure to complete returns null. Session expiry and required page visibility proofs remain mandatory and still reject the transaction.

The new transaction lifetime identifier is solely a work-budget key. Optional rollback/advisory restoration continues to invalidate the separate read-authority epoch. Rollback/release failure is fatal; optional recovery does not hide a damaged transaction.

## Bounded live navigation

- Each root or reply page examines at most 128 candidates, with one sentinel. A hidden-heavy scan can return an empty/partial page and an opaque continuation. A null cursor, not an empty array, indicates exhaustion.
- Root ordering remains pinned first, then the requested likes/time direction and existing timestamp/UUID tie breaks. Candidate timestamp coordinates retain PostgreSQL microseconds.
- Version-4 continuations are opaque server-owned references, scoped to account, authenticated session, post/root, page size, ordering/preview options and current classification scope. They never contain hidden IDs or sequences on the wire and never authorize content.
- Roots now use a current/live keyset rather than a whole-discussion snapshot. The last visible anchor must remain visible and retain its relevant ordering coordinates. Deletion, denial, pin changes, or relevant anchor-like changes require restart. Off-page changes can move content across a live boundary; refresh is necessary for a new complete ordering, as with other live discovery keysets. Old JSON discussion cursors explicitly restart.
- Reply previews emit a continuation for ordinary 20-row traversal, not for their 1–5-row preview size.
- Exact context first authorizes the explicit parent and exact child chain, then seeks directly around the target sequence. It returns at most two currently visible neighbors on either side, each found in a bounded 128-candidate window. A hidden-heavy neighborhood can be shorter. The target is never found by scanning the whole prefix. Context windows do not advance normal traversal.

## Indexed source ordering and synchronous writes

Migration `0168_community_discussion_order.sql` separates the mutable ordering projection from immutable content definitions. A locked cutover (`SHARE ROW EXCLUSIVE` on roots and like memberships) backfills exact integer counts and enrolls existing membership IDs without inventing event dates, then enables source triggers before releasing the locks. The migration can wait for active writers and performs one historical scan; it is not a concurrent/zero-downtime migration claim.

- Root time reads first fetch the singleton pin, then seek the current live-only time index. Time and like candidate reads use the live-only relation added in migration `0170`. All-ASC composite indexes support same-direction scans: ordinary `like_count` descending, or `-like_count` descending to preserve ascending-count/descending-time-and-UUID semantics. Nonnegative PostgreSQL integer counts make negation safe, including the maximum. Complete tuple intervals retain the post prefix in ordering and seek; ascending likes now use one normalized interval rather than separate equal-count/greater-count phases. The pin and all phases share one 129-coordinate allowance, never 129 plus a pin. Only selected coordinates load root data, ordering metadata and viewer-like facts.
- Reply enumeration has an approved, nondeleted `(post_id, root_comment_id, sequence)` partial index. It queries a closed-prefix composite-key interval and orders by the complete composite key in one direction, rather than scalar prefix equality plus global sequence order. Both interval endpoints have the exact requested post/root UUIDs; positive bigint sequence values are bounded by zero (exclusive) and bigint maximum (inclusive), with a strict cursor endpoint. This retains global sequence uniqueness while preventing its unrelated-scope ordering from satisfying the requested complete-key order. Stored hidden/tombstoned prefixes are excluded by the partial index. Runtime visibility still uses canonical current approval, parent, category, block and Media proofs; these indexes are not authorization.
- Index enumeration is unlocked. Selected roots are locked in stable UUID order before their projection rows, then current metadata is rechecked. Changed coordinates or split-query pin observations require restart. The visible anchor's pin state is also rechecked between its guard read and the successor scan. No global per-root like aggregate or top-N-before-sort substitute remains.
- Membership insert/delete triggers synchronously advance a unique predecessor event and projection; no-op conflicts emit no delta. A durable membership witness prevents replay and double removal. Fresh re-likes have fresh IDs. Root visibility/deletion transitions and permitted pre-approval timestamp edits update canonical ordering coordinates without changing the payload. Existing all-root parent/identity immutability remains unchanged, and approval-bound timestamps remain immutable. Trigger depth alone never authorizes a counter update: source identity, immutable creation transaction, predecessor, exact delta and canonical live metadata must all match. Counts remain nonnegative PostgreSQL integers; overflow aborts the source mutation.
- Runtime source writers are the existing Discussion mutation INSERT ON CONFLICT / DELETE path. Existing immutable membership UPDATE rules remain. Historical root/account FK retention and approval-bound deletion rules are not relaxed. Explicit permitted pre-approval root cleanup cascades only its empty ordering projection; event/membership witnesses remain retained. Source/projection TRUNCATE is rejected rather than silently desynchronizing counts. No existing runtime/maintenance TRUNCATE call was found.

All opaque root and preview cursor writes are queued per transaction and flushed only after every selected root/reply/author/media projection, including standalone comment, context and the legacy FeedService comment path. This avoids holding the per-account navigation quota lock across further domain reads; existing mandatory and optional final proofs still follow the flush.

The v5 rating-link dependency owner does not currently expose a shared monotonic optional-time budget. Discussion optional counts therefore return generic unknown before entering that dependency batch. This does not change mandatory content visibility, existing profile/liked count behavior, or a genuinely empty child set's exact zero.
