Local PostgreSQL, actual source/compiled CLI and strict compilation checks have passed within the exact-input scopes recorded in [READING_C27_INTEGRATION.md](READING_C27_INTEGRATION.md); cloud CI, password-authentication/Docker acceptance and actual production activation remain separate.

## Home 0178 worker upgrade

The Home-capable worker in this tree changes the deployment role contract. Before starting the current application/worker binary, apply the complete normal checksum/prefix-verified migration chain through `0180_identity_session_revocation_epoch.sql`, including the Home 0177/0178 predecessor. This follows the [Home activation](../apps/api/docs/HOME_PUBLICATION_ACTIVATION.md) and [registration guard](IDENTITY_REGISTRATION_GUARD.md) deployment contracts; 0178 is the Home worker upgrade boundary, not the current binary's migration cutoff. Then separately provision exactly two additional SELECT privileges: `whaleu_community.home_post_dispositions` and `whaleu_community.home_discussion_parent_bindings`. Do not add Home MAINTAIN, UPDATE, INSERT, DELETE, TRUNCATE or SECURITY DEFINER access. This source change performs no real production grants. The worker's exact role preflight fails closed on a 0176-only or partially installed Home schema. Historical 0176/0177 application schema inspection and source reads remain supported as compatibility paths; they do not authorize backward deployment of the current application/worker binary.

The original 0176 catalog collector, formatter, queue, retries, SQL source fences and 100 ms statement / 500 ms final-owner budgets remain unchanged. 0178 adds a separately pinned, finite historical Home-reading catalog seal. Managed initial and final schema proofs compare the combined original-reading and Home identities. The Home seal covers exact immutable-owner keys/constraints/index validity, canonical publication-xid invariants, enabled fresh/immutable/deferred/late guard attachments and finite Home definition/Review helper bodies. It does not look up current activation or admission values, so expiry or replacement does not retroactively deauthorize a valid historical source.

Only a managed transaction that retained that exact combined schema proof may read the two Home evidence rows without FOR SHARE. The permission is private to its PoolClient, actual transaction lifetime and read epoch; savepoint rollback/epoch replacement and transaction completion invalidate it. Other canonical consumers keep their original FOR SHARE reads. The removed locks are only the two new Home table SHARE locks; immutable exact-key rows, fresh-only insertion, existing source fences and same-transaction late guards remain. Before initial catalog inspection, managed retention takes the nonblocking transaction-shared counterpart of the exact existing MIGRATION_LOCK; the official migrator already holds that key session-exclusively. The shared gate remains held through final proof and COMMIT/ROLLBACK, so cooperating migrations cannot change dependency DDL in the final-check-to-COMMIT window. An active exclusive migration causes controlled unavailable rather than a wait. Standalone schema inspection, including optional presentation/capability observations that only inspect, does not acquire or claim this managed gate. The atomic cooperating-migration guarantee applies to retained required reading-owner transactions. Administrators who bypass the official migration gate remain a trusted boundary: pause and drain reading-related transactions before direct DDL changing dependency tables, constraints, triggers, functions or ownership. A same-transaction post-drain rejection test is not evidence for separate-connection migration exclusion; that requires the independent two-connection lock test. The narrow catalog is scanned at existing schema boundaries, not for every ancestor or SQL trigger.

## What schema readiness authenticates

The normal migration captures a catalog digest only after installing its fixed DDL. Runtime never updates that digest. Runtime pins the exact catalog-function body SHA and validates its SQL/invoker/stable/search_path/result metadata before executing it. The protocol must be the exact immutable literal shape/version/formatter/generation/migration and share the catalog function's owner.

The digest covers M2 relations/indexes, column/default definitions, constraints, functions/owners, enabled state and definitions of all M2 relation triggers plus named dependency late guards. Unknown extra objects, missing/disabled/modified guards or function bodies fail. Fixed slot IDs are separately exactly [1,2]. Ordinary job/result/lease data is not a schema fingerprint. Required write readiness is retained and checked again under the existing managed finalizer; optional reader readiness remains inside its optional checkpoint and cannot discard earlier canonical proofs.

The historical 0176-only inspection uses two bounded-object catalog queries; it does not scan source/job/result data except the two fixed slot IDs. The 0178 Home path additionally verifies its narrow collector/constant marker and captures the narrow catalog in two more queries. The normal-migration PG suite executed ten real two-query samples per locale on the frozen stage-v2: C median 7.522 ms/max 9.620 ms; en_US.utf8 median 8.386 ms/max 8.948 ms. These are measurements on fresh disposable clusters, not production latency or cost guarantees. The fixed existing final proof time budgets remain unchanged.

## Supported runtime role and trust boundary

The migration owner is a trusted deployment principal, not the runtime account. The formatting process must use a separately provisioned non-owner, non-superuser role whose credential is held only by this managed commit-owner process, not an interactive SQL client, arbitrary raw writer, user-facing HTTP tier or other job owner. Provisioning and secret custody require deployment review and are not performed by this patch.

The executable contract in role-contract.ts lists exact relation privileges and row-lock columns. SELECT supplies actual canonical/Review/Identity/Media reads. MAINTAIN supplies the existing SHARE table fences without table-wide UPDATE. Named UPDATE key columns are necessary for PostgreSQL SELECT FOR SHARE/UPDATE; these are not claims of business-write authority. Queue mutation is limited to UPDATE jobs/slots and INSERT results. The role cannot insert publication heads/jobs. All existing source/SQL guards and managed private permits remain mandatory.

The production preflight requires this bounded table/column contract and rejects extra application table/column write rights, extra table reads/MAINTAIN, schema CREATE, application relation/function/schema ownership or owner membership, executable application SECURITY DEFINER functions, superuser/CREATEROLE/CREATEDB/REPLICATION/BYPASSRLS, database CREATE, or SET session_replication_role permission. The schema and runtime role may require an explicit deployment-specific GRANT plan; nothing here grants permission.

This is a supported managed-runtime admission contract, not a universal SQL capability system. A credential holder with direct DML can still issue early SET CONSTRAINTS and idle until COMMIT; triggers cannot re-arm on arbitrary idle. Direct SQL with runtime credentials is forbidden by the supported deployment contract. The managed transaction wrapper alone owns commit, checks exact current owner/deadline facts after deferred waits, and then commits without unbounded application work. Trusted migration administrators can change guards and are outside the accidental-writer defense. A hostile-holder-resistant database operation API would require a separately reviewed permission model, not a claim that these triggers solve that problem.

Disposable PG tests create a NOLOGIN test role only in whaleu_test on loopback, grant exactly this contract, SET LOCAL ROLE inside the original managed finalizer, and remove the role in cleanup. They exercise real first publication processing and nonempty ancestor Media claim/completion, plus privileged/overbroad-role negatives. The normal-migration C/en_US suite executed successfully on runtime-identical stage-v2. A separate exact CLI-stage-v1 test also passed with a direct ephemeral restricted LOGIN over verified TLS, genuine queued-source processing, source and ordinary compiled entries, automatic serve shutdown after a tick, and privileged-login denial. This loopback-trust run did not prove password authentication or Docker CI. Disposable grants/roles are test evidence, not production provisioning.

PostgreSQL permission basis: https://www.postgresql.org/docs/18/sql-lock.html and https://www.postgresql.org/docs/18/sql-select.html. PG18 permits MAINTAIN for table lock modes; row-lock SELECT requires UPDATE permission on at least one column.
